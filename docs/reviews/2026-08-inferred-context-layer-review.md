## B. Findings by severity

### MAJOR

**B1. No committed, repeatable live-Supabase test exists for the new SECURITY DEFINER functions/RLS — the codebase's own established convention for exactly this class of risk was not followed.**
This codebase has a standing pattern for proving RLS/RPC behavior against a *real* Postgres instance, not just mocks: `supabase/tests/project_evidence.rls.test.ts` and `supabase/tests/project_records.rls.test.ts`, gated behind `SMARTFLOW_RUN_LOCAL_SUPABASE=1` (`describe.skip` otherwise) — this is precisely the pattern the prior review's finding R-3 names and calls "consistent with this codebase's existing convention for every other RLS-backed table." Task 3b added no `supabase/tests/inferred_project_context_fields.rls.test.ts` (or equivalent). Instead, the 11-check verification described in task 3b's report ran once against a disposable, hand-provisioned `docker run postgres:17` container with manually written scratch SQL, then the container was deleted (per the implementer's own account). That verification is real evidence the logic worked *once*, but it is not reproducible, not integrated into `npm test`, and leaves zero regression protection for `create_inferred_context_field`/`resolve_inferred_context_field`/RLS on this table going forward — unlike every sibling RLS table in this codebase. This directly fails this review's own checklist instruction ("live-gated where R-3's existing pattern requires").

**B2. `create_inferred_context_field` (and `resolve_inferred_context_field`'s `correct` path) omit ADR-0007's own established unique_violation race-handling pattern; a concurrent duplicate is misreported, not gracefully handled.**
`create_project_evidence_with_observation` ([`20260803000000_project_evidence_observations.sql:221-304`](../../supabase/migrations/20260803000000_project_evidence_observations.sql)) wraps its INSERT in an exception block, uses `get stacked diagnostics ... constraint_name` to confirm which constraint actually fired before treating it as benign, and fails closed (raises rather than fabricates) if the expected row can't then be found. `create_inferred_context_field` ([`20260807000000_inferred_project_context_fields.sql:306-349`](../../supabase/migrations/20260807000000_inferred_project_context_fields.sql)) instead does a bare `select ... limit 1` duplicate check *before* an unprotected `insert` — under two concurrent identical derivations, both transactions can pass the SELECT check and one INSERT then hits the partial unique index (`inferred_project_context_fields_fingerprint_key`) with **no exception handler at all**, propagating a raw Postgres error. In the Worker, this is caught per-candidate ([`context-derivation-endpoint.ts:600-603`](../../agent/worker/context-derivation-endpoint.ts)) and silently recorded as `results.push({ kind, outcome: 'persistence_failed' })` — a legitimate duplicate is misreported as a failure, corrupting the run's own `accepted_count`/`dropped_count` metadata (ADR-0009 Q3). The same gap exists in `resolve_inferred_context_field`'s `correct` insert; the migration's own comment (lines 456-462) claims "the caller can treat [a unique_violation] as already-applied," but `inferredProjectContextFieldRepository.resolve` ([`inferredProjectContextFieldRepository.ts:193-198`](../../src/features/projects/inferredProjectContextFieldRepository.ts)) has no code path that recognizes a raw `unique_violation` — it falls through to a generic, non-actionable `InferredContextFieldPersistenceError`. The comment's promise is not implemented.

**B3. ADR-0009 Decision §2's stated precedence rule is not implemented; the task-3b report's claim that precedence is built is not supported by the code.**
ADR-0009 states: "explicit evidence-extracted facts... outrank `user_confirmed`/`user_corrected` inferred fields, which outrank `proposed`... Conflicts... surface, never silently resolve." In `contextRebuildService.ts:252-261`, the base evidence-derived input and the inferred additions are flatly concatenated (`[...baseContextInput.objectives, ...inferredAdditions.objectives]`, etc.) with no precedence ordering, no suppression of a lower-tier duplicate, no explicit conflict marker. `contextRebuildInferredFieldsInput.ts`'s own header comment (lines 19-32) states outright: *"Precedence between MULTIPLE eligible fields of the same kind is deliberately NOT resolved here... Within this module alone, every eligible field kind maps straight through."* The only backstop is `projectContextBuilder.ts`'s pre-existing `MULTIPLE_ACTIVE_OBJECTIVES`/`MULTIPLE_ACTIVE_MILESTONES` checks ([`projectContextBuilder.ts:448-491`](../../src/features/projects/projectContextBuilder.ts)), which fire *only* when two or more entries share `status === "active"` — this catches nothing for decisions, risks, capabilities, or candidate actions, and nothing for two non-"active"-status objectives/milestones of different tiers. No test in `contextRebuildService.test.ts`'s new ADR-0009 describe block (lines 313-390) exercises a multi-candidate, mixed-tier scenario. This is a real gap between what ADR-0009 (Accepted) requires and what was built, and between what task 3b's final report claimed ("E. Builder widening implemented — precedence + marking evidence") and what the code actually does.

**B4. Dual-implementation divergence: the Worker's per-kind validation is measurably laxer than the canonical TS validator for date-shaped fields.**
`inferredProjectContextFieldValidation.ts`'s `optionalIsoTimestamp` (lines 64-68) requires `since`/`completedAt`/`decidedAt` to parse via `Date.parse` before accepting them. The Worker's `normalizeCandidate` (`agent/worker/context-derivation-endpoint.ts:411-434`) validates the same three fields with `isBoundedString(value, 40)` — a bounded non-empty string, nothing more; `"banana"` passes. Since the Worker is the only production path that creates model-authored candidates, and `contextRebuildInferredFieldsInput.ts` casts `field.content as InferredObjectiveContent` etc. directly with **no re-validation** before it reaches `ProjectContextBuilder`, and the builder itself performs no date-shape check on these fields either — a non-timestamp string accepted by the Worker's looser check flows unvalidated all the way into the built `ProjectContext`. This is exactly the "any divergence: MAJOR" scenario this review was asked to check for.

### MINOR

**B5. The narrow objective/milestone-only scope of automatic supersession is an undocumented, stricter-than-ADR-0009-text interpretation — this is the unexplained "refinement" (see D).**

**B6. No committed test verifies the migration's own SQL structure (columns, CHECK constraints, indexes).** Consistent with this codebase having no precedent for such a test on any other migration, but this review's own checklist listed "migration structure" as a required-minimum test category, and none exists as a repeatable artifact — only the now-destroyed disposable-container session (see B1, which subsumes this for the SECURITY DEFINER/RLS behavior specifically).

**B7. `create_inferred_context_field`'s `SOURCE_EVIDENCE_NOT_FOUND` check verifies each `source_evidence_id` belongs to the caller's own project, not that it belongs to the specific derivation run's actual evidence snapshot.** ([`20260807000000_inferred_project_context_fields.sql:288-298`](../../supabase/migrations/20260807000000_inferred_project_context_fields.sql)) Today this is safe only because the Worker's own `normalizeCandidate` (`context-derivation-endpoint.ts:385-391`) independently filters candidate `sourceEvidenceIds` against the run's own `validEvidenceIds` set before calling the RPC — the database itself does not enforce run-membership, only project/owner membership. A defense-in-depth gap, not a currently-reachable bug, since the one production caller (the Worker) already narrows correctly.

## D. The unexplained "refinement" — identified and classified

Task 3b's final report stated "one refinement was necessary" without naming it in its own §J. Comparing the migration against ADR-0009's Decision §1 text identifies it: ADR-0009's state machine says a field is superseded when "a newer derivation run produced a fresher candidate for the same project + contextFieldKind + logical slot" — general language, not limited to any subset of kinds. The implementation narrows this to **only** `kind IN ('objective', 'milestone')`, and only against other still-`proposed` rows from a different run (migration lines 317-340). This is a real, considered interpretation (documented at length in the migration's own SQL comments), and it is **strictly safer** than the ADR's ambiguous text: it never over-supersedes, it only ever leaves more candidates coexisting for the builder's own fail-closed validation to catch (project-domain.md §15). But it is **not** reflected anywhere in ADR-0009 itself or in the (still Task-3-vintage, never updated) design note — confirmed by grepping the design note for "logical slot," "supersession," and "narrow," all zero matches. Per this review's own instruction, an interpretation that is strictly safer but undocumented in the ADR/design note is classified **MINOR (doc gap)**, not a violation — recorded as B5.

## E. Dual-implementation equivalence result

## G. Recommendation

**Merge after listed fixes.** The core architecture (aggregate separation, authority semantics, RLS/SECURITY DEFINER posture, fail-closed validation discipline, backward-compatible optional dependency wiring) is sound and well-reasoned, and three of the four MAJOR findings are containment/precision gaps rather than authority-boundary violations — nothing here grants inferred content execution authority, nothing bypasses ownership checks, nothing here is exploitable for privilege escalation. But B1–B4 are concrete, evidence-backed gaps against this task's own explicit checklist and against ADR-0009's own accepted text, not stylistic nitpicks:

- B1 (no committed live-RLS/RPC test) should be closed before merge — it is a one-line-of-effort gap (copy `project_evidence.rls.test.ts`'s pattern) that removes the single largest verification risk in this changeset.
- B2 (race-safe duplicate handling) should be closed before merge — the fix is well-precedented in this same codebase (`create_project_evidence_with_observation`'s own exception block) and is a bounded, mechanical change.
- B3 (precedence) and B4 (date-validation divergence) can reasonably be deferred to a fast-follow **only if** the Product Owner is explicitly told, in writing, that ADR-0009 Decision §2's precedence rule is not yet implemented and that a mixed-tier-conflict scenario has never been tested — merging silently on this point would misrepresent the ADR's own accepted text as fully realized.
